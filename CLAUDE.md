# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`reminders-cli` is a macOS command-line tool for interacting with Reminders.app via EventKit, built with Swift Package Manager and Apple's `swift-argument-parser`.

## Commands

- Build (debug): `swift build`
- Build matching CI exactly: `swift build -Xswiftc -warnings-as-errors`
- Run all tests: `swift test` (or `swift test -Xswiftc -warnings-as-errors` to match CI)
- Run a single test: `swift test --filter RemindersTests.NaturalLanguageTests/testTomorrow` (filter format is `<Target>.<TestCase>/<testMethod>`, method optional)
- Release build (universal arm64/x86_64 binary): `make build-release`
- Full release package (tarball + shasums, as used for GitHub releases): `make package`
- Clean build artifacts: `make clean`
- Run locally without installing: `swift run reminders <subcommand> ...`
- Lint (as `.github/workflows/lint.yml` does): `swiftlint lint --strict`, `markdownlint-cli2`, `lychee --config lychee.toml README.md CLAUDE.md 'skills/**/*.md'`, `checkmake Makefile`, `yamllint --strict .`, `actionlint`, `git ls-files -z '*.sh' | xargs -0 shellcheck`, `git ls-files -z '*.json' '*.resolved' | xargs -0 -n1 jq empty`

Besides `-warnings-as-errors` on both library targets (applied in `Package.swift` and again explicitly in CI), `.github/workflows/lint.yml` lints every file type in one job per linter, all blocking: Swift with SwiftLint (`.swiftlint.yml`), Markdown with markdownlint-cli2 (`.markdownlint-cli2.yaml`) and its links with lychee (`lychee.toml`), the `Makefile` with checkmake, YAML with yamllint (`.yamllint.yml`), workflows with actionlint, shell scripts with shellcheck, and JSON syntax with jq. `CHANGELOG.md` is excluded, since release-please generates it. The linters' versions are in `mise.toml`, where Renovate updates them. Fix a finding rather than disabling its rule; a rule is only disabled or tuned in the config where it conflicts with a deliberate project pattern, with the reason next to it, and a single exception is a `// swiftlint:disable:next <rule>` with a comment saying why.

The `qlty` job in the same workflow runs `qlty check --all` with the security plugins enabled in `.qlty/qlty.toml` (zizmor and checkov for the workflows, osv-scanner and trivy for `Package.resolved`, gitleaks and trufflehog for secrets, ripgrep for `TODO`/`NOTE`/`FIXME` comments; the linters above aren't repeated there) and fails a PR that adds code smells (complexity, duplication) compared to `main`. Run `qlty check --all` and `qlty smells --all` locally before opening a PR. Split code that trips a smell rather than suppressing it; a finding that's intentional is ignored in `qlty.toml` with a `[[triage]]` entry narrowed to the rule and file, with the reason next to it. A `TODO`/`NOTE` comment for open work needs a GitHub issue: reference it in the comment (`// TODO(#124): ...`) and in its triage entry, and link the code lines from the issue. Don't reword such a comment to get past the check.

Coverage on Codecov combines two sources: the unit tests, and an instrumented build that the `live-test` job in `.github/workflows/mr-test.yml` runs through `.github/scripts/live-test/live-test.sh` against a real store on a runner. The `upload-coverage` job merges both into one upload, so code that needs the EventKit store (the `Reminders` methods and the subcommands' `run()`) is covered by extending `live-test.sh` on its throwaway lists, not by unit tests.

## Architecture

Execution flows in one direction through four layers:

1. **`Sources/reminders/main.swift`** — entry point. Requests Reminders access via EventKit (branches on macOS 14+ `requestFullAccessToReminders` vs. the older `requestAccess(to:)`), then hands off to `CLI.execute()`. `AccessRequirement.swift` decides when to skip the request: `--help`/`--version`/completion flags, ArgumentParser's `help` subcommand, and the `doctor` subcommand, which must only report the authorization state and never trigger the prompt. A denied access request is reported as `CLIError.accessDenied` using `OutputFormat.detect(in:)` on the raw arguments, since nothing has been parsed yet.
2. **`Sources/RemindersLibrary/CLI.swift`** — the `CLI: ParsableCommand` root (command name `reminders`) and one private struct per subcommand (`ShowLists`, `ShowAll`, `Today`, `Overdue`, `Upcoming`, `Show`, `Add`, `Delete`, `Edit`, `Postpone`, `NewList`, `DeleteList`, `Doctor`), all adopting `FormattedCommand` (a `ParsableCommand` that exposes its `--format`). `complete` and `uncomplete` are one generic `SetCompletion<Mode>`, registered once per `CompletionMode` (`CompleteMode`, `UncompleteMode`), which supplies the command name and the state it sets. The filter options `show` and `show-all` share live in the `@OptionGroup` `ReminderFilterOptions`, which also validates them and builds the `ReminderFilter`. Each subcommand only declares its `@Argument`/`@Option`/`@Flag` properties and a thin throwing `run()` that delegates to a single shared `Reminders()` instance. `CLI.runCommand(_:)` parses and runs one command and returns a `CLIRunOutcome` (used by `Tests/RemindersTests/CLIRunTests.swift`); `CLI.execute()` is the single place a `CLIError` is written to stderr and turned into its exit status. Any other error (help, version, `ValidationError`) is handed to ArgumentParser's `exit(withError:)` unchanged. Shell-completion for list names is wired up here via `listNameCompletion(_:_:_:)`.
3. **`Sources/RemindersLibrary/Reminders.swift`** — the `Reminders` class wrapping `EKEventStore`/`EKReminder`/`EKCalendar`, with one method per subcommand (show, add, edit, postpone, complete/uncomplete, delete), along with `OutputFormat`, `DisplayOptions`, and `Priority`. The list commands (`showLists`, `newList`, `deleteList`, `runDoctor`) are an extension in `Reminders+Lists.swift`. Methods never print errors or call `exit`; they `throw CLIError` and only print success output to stdout. Since EventKit's reminder fetch is callback-based, `fetchReminders(on:displayOptions:)` wraps it once with a `DispatchSemaphore` so the command methods are plain synchronous, throwing code; it uses EventKit's faster incomplete-reminders predicate for `.incomplete` and returns nothing for an empty list of calendars (which EventKit would read as every list). Every write goes through `reportingSaveFailure(action:_:)` (in `CLIError.swift`), which reports any store error as `save_failed`. The methods only fetch and save; the logic around them lives in EventKit-store-free functions in topic files, so it's testable on unsaved in-memory reminders (`ReminderChangeTests`, fixtures in `InMemoryReminderTestCase`):
   - `ReminderChanges.swift` — what a command changes on a reminder before saving: `configureNewReminder` (`add`), `applyEdit` (`edit`, split into small steps for fields and repeat rules), `applyPostpone` (`postpone`, with the `PostponeTarget` that `Postpone.validate()` and `run()` build from the date argument or `--next-weekday`), all setting the due date through `setDueDate(of:to:)`, which replaces the alarms with one at the due time only for a timed due date; and `affectedOutput` (the confirmation of `complete`/`uncomplete`/`delete`/`edit`/`postpone`).
   - `ReminderFilter.swift` — `ReminderFilter`, the filter and sort options of `show` and `show-all` as one value, whose `apply(to:now:)` sorts and filters fetched reminders; `ShowAllQuery` builds one too.
   - `ReminderFormatting.swift` — the plain output (`format(_:id:listName:)`, due date and repeat texts), `EKReminder.displayId`, `isOverdue(_:now:)`, and the filter predicates `matchesDueOn` (`--due-date`/`--include-overdue`) and `matchesAdditionalFilters`.
   - `Resolution.swift` — resolving list and reminder arguments (see below) and choosing the source for `new-list` (`selectListSource`).
   - `Recurrence.swift` — `Recurrence`, building and updating repeat rules, `validateRecurrenceSchedule` and `nextOccurrence`.

   Keep new command logic in functions like these and leave only fetching and saving in the methods.
4. **`Sources/RemindersLibrary/CLIError.swift`** — the one error type the CLI reports: a stable `Code` (`list_not_found`, `reminder_not_found`, ...) plus `message` and optional `suggestion`, a 1:1 `exitCode` per code (2–13; 1 is reserved for non-`CLIError` failures, 64 is ArgumentParser's usage error), and `rendered(format:)` for the plain (`Error:`/`Suggestion:` lines) and JSON (`{"error":{...}}`, single line) shapes documented in the README's "Errors" section. Add a new failure mode by adding a `Code` case and a static constructor; the exhaustive switches in `exitCode` and in `CLIErrorTests` force the mapping and a test sample to be added too.
5. **Supporting extensions**, used by the layers above:
   - `NaturalLanguage.swift` — `DateComponents(argument:)` (`ExpressibleByArgument`), parses natural-language date strings like `"tomorrow 9am"` for `--due-date` options via `NSDataDetector`. Known limitation: `"next weekend"` doesn't parse (Apple Feedback FB8921206), covered by a test expecting `nil`.
   - `ShowAllQuery.swift` — the `show-all` parameters behind the `today`, `overdue` and `upcoming` convenience commands, built by `ShowAllQuery.today/overdue/upcoming(...)` (which take `now`/`calendar` so `ShowAllQueryTests` can pin the dates) and run through `Reminders.showAllReminders(_:outputFormat:)`. These commands must stay free of filter logic: a new shortcut is a new builder, not a new code path.
   - `ReminderSelection.swift` — the EventKit-free expansion of the reminder ID arguments of `complete`, `uncomplete`, `delete` (variadic) and `edit`, `postpone` (one argument): comma-separated IDs and `-` for newline-separated IDs on stdin (injected for tests). `isBatch` depends only on the raw arguments and picks the JSON shape: the single object for one plain ID, an array otherwise. `Edit.validate()` uses it to reject new text on a batch. The commands resolve every ID with `resolveReminders(_:idsOrPrefixes:onList:)` before changing anything, stage the changes in memory (`eventStore.reset()` on any error), and save or remove them with `commit: false` followed by one `eventStore.commit()`.
   - `Sort.swift` — `Sort`/`CustomSortOrder` enums backing `show --sort`/`--sort-order`, plus `ListSort` backing `show-lists --sort`.
   - `RepeatDays.swift` — `RepeatDays`, the parsed `--repeat-on` day set (names, `weekdays`/`weekends` aliases, de-duplicated and Sunday-first), plus `plainWeekdays(of:)`, which reads a rule's days only when none carries a week number (so "last Friday of the month" isn't reported as plain days). It backs the plain `on Mon, Wed` suffix, JSON `recurrenceDays` and the weekly-on-days branch of `nextOccurrence`.
   - `ListSummary.swift` — the `ListSummary` value type behind `show-lists` plus the EventKit-fetch-free `summarizeLists(_:reminders:now:includeCompleted:)` and `formatListSummaries(_:)`, so the per-list counting and the aligned plain output are unit-testable. Counts come from one fetch over all calendars (`fetchReminders(on:displayOptions:)`, with completed reminders only for `--include-completed`), bucketed by `calendar.calendarIdentifier`. "Overdue" is the free function `isOverdue(_:now:)` in `ReminderFormatting.swift`, shared with `show --overdue` so the two views can't disagree.
   - `PrettyOutput.swift` — `--format pretty` for the reminder listings (`show`, `show-all`, `today`, `overdue`, `upcoming`). These commands take `ListingFormat` (`plain`/`json`/`pretty`) through the shared `@OptionGroup` `ListingOptions` instead of `OutputFormat`, so no other command accepts or has to handle `pretty`; `ListingOptions` also resolves the `REMINDERS_FORMAT` default, rejects `--verbose` without `pretty`, and maps `pretty` errors to plain via `errorFormat`. The rendering itself is the EventKit-free `formatPretty(_:now:calendar:style:verbose:)` over `PrettyRow` values (built from an `EKReminder`), with the due column from `prettyDueText` and colour through `PrettyStyle` (only on a TTY without `NO_COLOR`). The `plain` format (`format(_:id:listName:)` in `ReminderFormatting.swift`) must stay byte-for-byte unchanged; `PrettyOutputTests` pins it.
   - `Doctor.swift` — the EventKit-free model behind `doctor`: `ReminderAuthorization` (mapped from the raw status value so the deprecated `.authorized` is never referenced), `DoctorReport` whose `checks` derive both the plain lines (`formatDoctorReport`) and the JSON `problems`, and `isHealthy` (no `fail` problem → exit 0, else `ExitCode.failure`). `DoctorProblem` codes are separate from `CLIError.Code` since nothing is thrown. Also the Darwin lookups: `findParentProcess` walks ancestors via `proc_pidpath`/`proc_pidinfo` to the first `.app` (TCC grants are per app), with the lookups injected for tests. `Reminders.runDoctor(outputFormat:)` gathers the EventKit data, and only with full access.
   - `Flagged.swift` — read-only `EKReminder.isFlagged`, backing plain output's `(flagged)` suffix, JSON `isFlagged` and `show --flagged`. EventKit has no public flag API, so it walks the undocumented `flaggedKeyPath` (`backingObject` → `_reminder` → `flaggedContext` → `flagged`) with `readFlag(from:keyPath:)`, which checks `responds(to:)` before every `value(forKey:)` (an unknown KVC key raises an uncatchable `NSUndefinedKeyException`) and falls back to `false`. Writing the flag isn't possible through EventKit (issues #51, #63); don't add `setValue(_:forKey:)` along this path.
   - `EKReminder+Encodable.swift` — manual `Encodable` conformance for `EKReminder`, used for `--format json` output. Its `EncodingKeys` enum is mirrored by the JSON field table in `skills/reminders-cli/SKILL.md` (the agent skill shipped by the Claude Code plugin in `.claude-plugin/plugin.json`); update the table in the same order whenever a key is added or removed, or CI (`.github/scripts/check-skill-json-fields.sh`) fails.

When adding a new subcommand: add a `FormattedCommand` struct in `CLI.swift` (with a `--format` option so errors can be rendered as JSON), register it in `CLI`'s `subcommands`, and implement the actual behavior as a throwing method on `Reminders` in `Reminders.swift` — keep `CLI.swift` limited to argument parsing/dispatch, and report failures by throwing a `CLIError` rather than printing or exiting.

Reminder items are looked up only by their stable `calendarItemExternalIdentifier` (never by list position) via the free function `resolveReminder(_:idOrPrefix:onList:)` in `Resolution.swift`, which accepts the full ID or a case-insensitive prefix of at least `minimumIdPrefixLength` (4) characters and throws `reminder_ambiguous` when a prefix matches several reminders; the string matching itself is the EventKit-free `matchIdentifier(_:idOrPrefix:minimumPrefixLength:)` so ambiguity is testable. Lists are resolved the same way by `resolveCalendar(_:nameOrId:)` (exact ID → exact title → case-insensitive title → unique case-insensitive substring, else `list_ambiguous`/`list_not_found`). The destructive `delete-list` uses the stricter `resolveCalendarExactly(_:nameOrId:)` instead: no substring step, and several lists sharing the matched title are `list_ambiguous` rather than first-wins; its refusal/confirmation rules are the EventKit-free `checkListDeletion(...)`, tested in `DeleteListTests`. `resolveReminder` and `resolveCalendar` are exercised directly in `Tests/RemindersTests/IdentifierTests.swift` (via `@testable import RemindersLibrary`) alongside `Tests/RemindersTests/NaturalLanguageTests.swift`'s natural-language date parsing tests.

## Release process

Releases are automated via [release-please](https://github.com/googleapis/release-please): merges to `main` accumulate into a release PR (version bump driven by Conventional Commits, tracked in `version.txt`/`.release-please-manifest.json`/`release-please-config.json`). The release PR is never merged when it is opened: `.github/workflows/release-automerge-weekly.yml` squash-merges it every Sunday at 18:00 UTC if its checks pass (run it via `workflow_dispatch`, or merge the PR by hand, to release earlier). Merging that PR tags the commit and creates a **draft** GitHub Release. The same `release-please.yml` run then calls `.github/workflows/publish.yml` as a reusable workflow, which checks out the release commit, runs `make package` to build the universal release binary/tarball, attaches `reminders.tar.gz` to the draft, publishes the release, and pushes an updated formula to the `udondan/homebrew-software` tap (`brew install udondan/software/reminders-cli`).

The release must stay a draft until the tarball is attached: this repository has GitHub's immutable releases enabled, so assets cannot be added to a release after it is published, and the tag name of a published release can never be reused. Draft releases do not trigger `release` workflow events, which is why publishing is chained from the release-please workflow instead of listening for a release event. `force-tag-creation` must stay enabled together with `draft`: a draft release has no tag, and without the tag release-please cannot find the release it just created, treats the repository as unreleased, and opens another release PR for the same version on every run. If the publish job fails, leave the draft in place and re-run `publish.yml` via `workflow_dispatch` with the draft's tag and the release commit; re-running release-please does not recreate an existing release.

The CLI's `--version` output is backed by `Sources/RemindersLibrary/Version.swift`, which release-please keeps in sync with `version.txt` via an `extra-files` generic updater — don't hand-edit the version in either file outside of a release-please PR.
